根因结论

唯一真正的冲突： ListRecords 在做关键词/分类/剧目/折子/演员筛选时，通过 LEFT JOIN record_artists / record_dramas / record_zhezis 做过滤。当一条记录关联多个实体（如多个演员）时，JOIN 把同一行复制成多份。

为什么 Safari 暴露、Chromium 没暴露： 前端用 {#each records as r (r.id)} 做 keyed 渲染。Safari/WebKit 遇到重复 key 会直接抛 each_key_duplicate 并中止渲染（页面卡在骨架屏/空白）；Chromium 只是静默重复卡片，不易察觉。

修复： 在 backend/internal/db/db.go 的 ListRecords 起始处改为 SELECT DISTINCT。所有被 SELECT 的列都来自 records 主表本身，JOIN 仅用于 WHERE 过滤，重复行数据完全一致，DISTINCT 安全折叠。该修复一次性覆盖了所有调用方（首页、搜索、分类、城市、Drama/Artist 详情）。

其余已确认无风险的点

• 统计/仪表盘/日历： 均为 COUNT(*) / GROUP BY 聚合，无 JOIN 放大。
• backfill* 系列（DramaIDs/ZheziIDs/ArtistIDs）：先收集唯一 id → IN 子查询 → 按 record_id 映射，与行数无关、安全。
• 前端 keyed each： 所有用了 key 的列表均基于 .id（categories/dramas/artists/records/zhezis），后端这些列表 id 唯一；无 key 的 each（artist_names、covers 等）即使有重复值也不会触发 duplicate 报错。
• 排序/分页： 当前前端一次性加载全量（无分页），ORDER BY date DESC 在 SELECT 字段内，DISTINCT 不冲突。
